## 1. What the product is

Graph-based hobby discovery. You pick interest clusters, explore a living graph,
and collect hobbies. **47 hobbies across 11 clusters** (`fitness, creative,
outdoor, tech, social, culinary, adventure, nature, craft, mind, community`),
all from curated typed data in `src/data/activities.ts` + `edges.ts` — the same
files exist in both repos and should stay in step.

**The graph is deterministic.** Activities, tags and edges are never generated by
AI. AI is confined to the two Groq routes this repo already has
(`/api/create-niche`, `/api/rabbit-hole`) and must never sit in front of core
navigation.

Domain: **aspectniche.com**. Live pages: `/`, `/demo`, `/privacy`, `/terms`,
`/support`, `/i` (invitation), `/r` (reply).

## 3. Design system

Read this once; it covers every screen. **Do not restate these rules per
component — they are global.**

### Themes are data, not code
`src/lib/themes.ts` is the single source of truth. A theme owns colour, **type**,
node rendering (`mark`), ambient motion (`ambient`), chrome density (`chrome`)
and `graph.backdrop`. Components branch on tokens and never hardcode a colour, a
font, or an animation decision. Adding a theme is one object; if you find
yourself editing a component to add a theme, the missing thing is a token.

Eight themes: **midnight** (default — cosmos, matches /demo), **aurora**,
**daybreak**, **glass**, **gallery** (warm paper; the light sibling — the
*ground* carries the yellow and `surface` is the lighter of the two),
**gallery-night**, **obsidian** (one lavender accent, no starfield, near-square
corners, Inter throughout, hues deliberately narrowed to lavender→slate),
**pocket-tech** (blue hour; smoked glass, satin silver, the only theme whose
backdrop is a drawing). Web also has **playground**; mobile does not.

`theme.graph.backdrop` decides what sits behind the graph: `cloud` (cosmos
wash), `none` (gallery paper), `ribbons` (Pocket Tech wallpaper, kept as path
data so it scales with no asset pipeline).

### The nine rules that hold everywhere
1. **A list is rows, not cards.** Hairlines and type separate; the only boxed
   things are controls. A bordered box gives every entry a button's silhouette.
2. **Exactly one filled control per screen**, and it names the next action.
   Never leave a button sitting there to report state.
3. **Facts are stated, not pilled.** Label-over-value grid, never bordered
   chips. A chip with no action renders as plain text, by contract.
4. **Everything tappable answers a finger** — an explicit press/hover state on
   every interactive row.
5. **A wide gap between the headline and everything under it.** Title in the
   display face → small dim lede → muted caps. Read from the type scale, never
   from literals.
6. **One accent per screen.** Repeated state uses opacity or the muted tone.
7. **Split a long surface rather than scrolling it.** A hobby opens as a card of
   three panes — Plan / About / Progress. **About is never gated**; deciding
   whether a hobby is worth collecting is exactly what it answers.
8. **Each pane owns a colour and it never touches type.** Pane tints drive band,
   border and tab rule only — never the ground behind body copy.
9. **No emoji in user-facing strings. Ever.**

Every interactive element needs default, hover/pressed, selected, disabled and
empty states. Colour changes must clear **WCAG AA** — the mobile theme test
fails the build rather than let a palette drift, and the web should match.

### Gallery's extra rules
Category reads through **motif, not colour** (one graphite, the sigil carries
meaning — do not reintroduce per-category hues). Nothing nests. Type carries
emphasis, never weight (two families, 400/500 only; serif italic reserved for
hobby and interest names). Motion is a page turn — no overshoot, no ambient loop.

### Type
Cosmos themes: **Space Grotesk SemiBold** display + **Inter** 400/500/600.
Gallery themes: **Instrument Serif Italic** display + **Inter Tight** 400/500.
Scale (mobile pt, mirror on web): title 30/36, displayLarge 28/34, display
20/26, heading 16/24, body 15/22, description 14/21, lede 14/20, chip 12/16,
caps 10 with 1px tracking, uppercase.

### Icon sets belong to the user, not the theme
Six sets: **obsidian, files, clean, retro, gallery, pocket**. The choice sits
beside the theme because a theme owns colour/type/motion and someone who wants
paper does not necessarily want folders.

All four curved kits draw the same **105 pictograms** — that is what makes them
one table and four sets. Every set draws all 47 hobbies and all 11 clusters;
a gap falls back to the cluster mark, which puts one drawing on ten hobbies.
Tests enforce this on both sides.

Every pictogram sits on the same **24-unit box**, which is why one switch
repaints every surface with no call site resizing. What differs is the carrier
behind it (kit's own 80-unit box, mapped in). `HobbyMark` is the only component
that reads the set.

**Four of the six ignore the theme** — Files is the browser's blue, Retro
brushed metal, Paint pigment, Pocket Tech satin silver; recolouring them per
cluster stops them reading as the object they are. Obsidian and Clean take the
theme's hue. Paint's pigment rotates per icon from four colours and therefore
carries **no meaning** — nothing should read one out of it.

The tab/nav bar stays monochrome in every set: an icon has to travel between
active and inactive tint at 22pt, which a blue folder or a metal jewel does not
survive. The six sets resolve to two drawings there.

### The rabbit is the mark
`BrandMark` draws a rabbit as a constellation — connected vertices tracing the
silhouette, one accent node at the nose. It is the **only** constellation in the
app; hobby marks are pictograms and graph nodes are orbs. Geometry is a point
list run through a closed Catmull-Rom spline, not hand-authored beziers, so
moving a vertex is editing one number. Below 40pt the interior vertices drop and
the stroke thickens — a constellation does not survive being shrunk. The nose
accent is never dropped.

**The logo is a supplied image and must not be redrawn.**

## 4. Feature inventory

Ordered by how much each matters to the web.

### Worth porting
- **The graph flips.** One side is discovery (what there is), the other the
  collection (what you have); tapping a hobby there focuses it and sprouts its
  own photos and pinned notes. **Nothing on the flipped side is invented** — an
  edge survives only where *both* ends are collected, and in focus every edge
  runs hobby→entry, never entry→entry. Two photos a month apart are about the
  hobby, not each other. *Already on web (`lib/flipGraph.ts`).*
- **Memory Walk.** Cinematic camera over the flipped graph, optional stops on
  notes, plus a collage. Owns no data — the queue is rebuilt from the same
  photos and notes the graph draws. **One timer and one transition, ever**;
  every manual move cancels the pending one and callbacks carry an epoch.
  *Already on web.*
- **Plan a Date** — three controls, not three lists. Budget is a **drag bar from
  free to no limit** snapping to a ladder (a budget is a decision; "up to $63"
  is the slider's opinion). The open end is a large sentinel, never `Infinity`,
  because JSON turns that into `null`. Food is **which meal**, not which cuisine,
  multi-select. Availability is a **calendar**, adding to a list rather than
  replacing a value. *Already on web.*
- **Invitations are links.** No server: the whole event is encoded into the
  link, so it opens for someone who has never installed anything. The answer
  travels back the same way. **A guest list is therefore who has replied and the
  host has opened, not a live roster** — stated on screen, never hidden. Wire
  format is a positional array with base36 epoch minutes and trailing blanks
  trimmed: 207 chars → 126. Positions never change meaning; new fields append.
  *Already on web (`/i`, `/r`).*
- **Three ways to look at a list** — list / grid / gallery, one preference
  across every screen. Gallery is deliberately the slowest: list asks which to
  read about, grid asks how many there are, gallery asks what this one *is*.
  There is no columns mode (needs a hierarchy; the catalogue is flat).
  *`lib/viewMode.ts` — not yet on web.*
- **Graph Studio** — a bottom panel of knobs, every one a lever the canvas
  already had. It is **not** a second theme system; it sits on top of the
  resolved theme. A knob added later is missing from an older stored config, so
  hydration merges over defaults rather than trusting the blob.
  *`lib/studio.ts` — not yet on web.*
- **Streaks, badges, discovery scoring** — `lib/streaks.ts`, `lib/discovery.ts`.
  Pure and portable.

### Phone-shaped — port the idea, not the code
- **Plans** — one merged list of scheduled sessions, invitations sent,
  invitations accepted and agreed date plans (`lib/agenda.ts`). A merge, not a
  copy, so cancelling something removes it on the next render. A **declined**
  invitation is left out (a list of things you are not doing is not an agenda);
  an **unanswered** one stays, because that is what needs chasing. A date plan
  appears only once both people agreed a window. `isPast` splits on the *end*
  time so a class you are halfway through still reads as today.
- **Reminders** (`lib/reminders.ts` + `notify.ts`) — local notifications as the
  alternative to the calendar, not an addition. Scheduling is a **diff**, never
  a teardown. iOS holds at most 64 pending, so the list truncates to the
  soonest. No web equivalent unless you want the Notifications API.
- **Calendar hand-off** — needs FULL access, not write-only; every route to an
  event editor is a *read*. Saving a session never requires it (switch,
  defaulting on).
- **Photos, places search, maps hand-off, haptics.**

### Accounts and sync — the newest work
Optional twice over: optional for the person (the app is complete signed out,
nothing behind a login) and optional for the build (with the two Supabase env
vars unset the client is null and the account UI is absent).

Sign-in is a **six-digit email code** — no password to leak, and no magic link,
because a link means registering a deep link and losing the hand-off whenever a
mail client opens it in its own webview.

**The device stays the source of truth.** `lib/sync.ts` merges and never
replaces; whole-document last-write-wins is the obvious implementation and the
wrong one, because two devices used offline would mean the second to reconnect
erases the first one's afternoon. So the document splits:
- **A record merges by union** — a hobby collected, a note pinned, a day the app
  was opened. Both sides are true, and the merge gives the same answer whichever
  device runs it. Collect dates keep the **earlier** one.
- **A preference goes to the newer document** — two themes do not add up to a
  third. `updatedAt` is stamped on every write and settles only these.

**Photos never sync** — the URI is a path inside the app's sandbox, so the row
copies across perfectly and points at nothing. Drafts stay local too.

If the web ever gains accounts it should share this schema and merge policy
exactly. The table is one row per user (`user_state`: `user_id`, `state` jsonb,
`updated_at` bigint) with four explicit RLS policies. **RLS is the only thing
protecting the data** — the publishable key ships in the client.

Setup gotchas that cost hours: the dashboard's "Data API URL" includes
`/rest/v1/` and must be stripped; the `anon` key is now the **publishable** key
on its own page; and **custom SMTP is required**, not optional, because Supabase
gates email-template editing behind it — and both the *Confirm signup* and
*Magic Link* templates must be changed to send `{{ .Token }}`.

## 5. Assets

Everything lives in `aspect-niche-mobile/assets/images/`.

- `icon.png` — 1024×1024 app icon.
- `logo-mark.png` / `@2x` / `@3x`, and `logo-mark-ink*` for light grounds.
- `logo-glow.png`, `splash-icon.png`, `splash-icon-ink.png`.
- `favicon.png`, Android adaptive layers (`android-icon-{background,foreground,monochrome}.png`).
- `tabIcons/` — raster nav icons (the app draws vector ones instead).

Icon kits are **committed path data**, not image files, in `graph/iconKits.ts`,
`curveKits.ts` and `themeKits.ts`. The original kit folders were downloads and
are gone; the repository is the record of what they drew, and
`scripts/build-icon-kits.py` falls back to the committed table. Regenerate with
that script rather than editing the generated files by hand.

Fonts come from `@expo-google-fonts` on mobile; on web use `next/font/google`,
which **self-hosts at build time** so no request ever reaches Google — that is
deliberate and is what keeps the site clear of the German GDPR problem.

## 6. Legal and compliance already in place

Governing law **New York**; audience **18+**. `/privacy`, `/terms` and
`/support` are live and were written against the real behaviour of both
properties — the privacy policy covers the site's two Groq API routes, not just
the app. Verified in-browser: **zero cookies, zero third-party hosts, zero
tracking**, which is why there is no cookie banner and none is required. WCAG AA
contrast was measured and fixed across the site.

The owner's email address appears publicly on `/privacy` and `/terms`.

## 7. Conventions

- **Commits:** no attribution trailers were used historically on this project;
  match the surrounding log.
- **Verification:** `npx tsc --noEmit` clean, `npx vitest run` green. Mobile is
  at 466 tests; the logic suites are the no-drift guardrail and pure modules are
  deliberately free of framework imports so they test without a device.
- **Pure module, then the screen.** Every non-trivial feature is a tested pure
  module plus a thin view. Follow it.
- Ask before rewriting `globals.css` — an earlier blanket append was rejected.
